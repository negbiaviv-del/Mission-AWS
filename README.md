## 📋 Project Overview
This project presents an advanced, secure, and distributed cloud architecture using a **3-Tier Architecture** model on **AWS**. The entire system is provisioned and managed utilizing **Infrastructure as Code (IaC)** and **Configuration as Code (CaC)** methodologies, enabling full reproducibility, high reliability, and a **One-Click Deployment** process.

The system consists of a seamless integration between four main domains:
1. **Infrastructure Provisioning (IaC):** Utilizing **Terraform** to build the physical backbone on AWS (Networking, Compute, Database, Storage, and Notifications).
2. **Configuration Management & Automation (CaC):** Utilizing **Ansible** to install dependencies, manage crucial environment variables, and dynamically spin up containers in a secure manner.
3. **Containerization:** Packaging the Backend service using **Docker** to ensure a consistent runtime environment.
4. **Application Layer:** A Flask (Python) interface that allows users to request server provisioning and configuration management, while saving data to **RDS**, backing up configuration files to **S3**, managing task queues with **SQS**, and triggering real-time email alerts via **SNS**.

# 🛠️ Tech Stack
* **Cloud Provider:** AWS (VPC, EC2, ALB, RDS PostgreSQL, S3, SQS, SNS)
* **Infrastructure as Code:** Terraform 1.14.9
* **Configuration Management:** Ansible
* **Containerization:** Docker
* **Backend Application:** Python 3.x, Flask, Boto3 (AWS SDK), Psycopg2 (PostgreSQL Driver)
* **Frontend UI:** HTML5, Tailwind CSS, FontAwesome

## 🗂️ Component Breakdown & Logic

### 1. Infrastructure Layer (Terraform)
The infrastructure is written modularly (Reusable Modules) and is divided into dedicated directories:
* **Networking:** Provisioning a VPC, public subnets for the ALB and Application, and secure private subnets for the database.
* **Load Balancer (ALB):** Managing and routing traffic to the application servers with high availability.
* **RDS (PostgreSQL):** Provisioning a managed database within a private `aws_db_subnet_group`, completely blocked from external internet access and accessible only by the App tier.
* **S3 Bucket (`new-mission-bucket`):** Used to store JSON configuration files generated by user requests.
* **SQS Queue (`mission-queue`):** Managing an asynchronous task queue that receives messages containing S3 file paths for future decoupled processing.
* **SNS Topic (`aviv-project-alerts-v2`):** An alert mechanism connected to the system administrator's email to receive real-time notifications for successful creations or deletions.

### 💡 Terraform State Management
The project currently manages the Terraform state locally (`terraform.tfstate`). For a single-developer environment or academic submission, local state management is sufficient and simplifies the initial provisioning process. However, in a production CI/CD environment with multiple engineers, the state should ideally be migrated to a remote backend (such as an S3 bucket with DynamoDB for state-locking) to ensure consistency, prevent race conditions, and securely store sensitive infrastructure data.


### 2. Configuration & Deployment Layer (Ansible)
The Ansible Playbook manages the complete lifecycle of the server from initialization to application runtime:
* **Base Package Installation:** Installing and starting the Docker engine and adding the `ec2-user` to the appropriate permission group.
* **The Dynamic Pipeline Solution:** To avoid hardcoding values that change upon recreation (such as the RDS Endpoint), the deployment utilizes Ansible's smart `lookup('pipe', ...)` feature. During file template creation, Ansible fetches the live output directly from the Terraform State and injects it into the configuration file.
* **Lifecycle Management & Overwrite Prevention:** To prevent a static local `.env` file from overwriting the dynamic runtime configuration, the Ansible task execution order is strictly enforced. Step 1: Copy the Backend source code to the server. Step 2: Dynamically generate and inject the `.env` file into the server. Step 3: Build the Docker Image and run the container using the `--env-file` flag.

### 3. Application Layer (Flask Backend)
The `app.py` code implements a highly reliable and fault-tolerant architecture (Robustness):
* **Input Sanitization:** When pulling environment variables in automated CI/CD pipelines across different operating systems, hidden characters (like Windows Line Endings `\r`) or trailing spaces can be introduced. The code utilizes the `.strip()` function on critical variables (especially the SNS ARN) to ensure these characters do not cause AWS API request rejections.
* **Creation Workflow:** The sequence operates as follows. First, the user fills out the machine requirement form (quantity, OS, launch script, etc.). Next, the data is saved into the `mission_data` table in the RDS database. The complete JSON payload is then generated and uploaded to the S3 Bucket. Following this, a decoupled, lightweight message (containing only the Bucket name and Object Key) is dispatched to SQS. Finally, a formatted, detailed alert is published to the SNS Topic, delivering an email notification directly to the registered user.

## 📋 Project Overview
This project presents an advanced, secure, and distributed cloud architecture using a **3-Tier Architecture** model on **AWS**. 4. **Application Layer:** A distributed application featuring a Backend API (Flask) and a background Worker, integrated with **RDS**, **S3**, **SQS**, and **SNS** for asynchronous processing and alerting.

## 🏗️ Architecture & Component Breakdown

### 1. Infrastructure Layer (Terraform)
The infrastructure is written modularly, creating a highly secure environment:
* **Networking (VPC):** Provisioning public subnets for the Frontend/ALB and secure private subnets for the Backend, Worker, and Database.
* **Compute (EC2) & Load Balancing (ALB):** Managing and routing traffic to the internal application servers via a Reverse Proxy setup.
* **Database (RDS PostgreSQL):** Provisioned within a private `aws_db_subnet_group`, completely blocked from the external internet and accessible only by the internal App tier.
* **AWS Services (S3, SQS, SNS):** Provisioning storage buckets for configurations, an asynchronous message queue (`mission-queue-v2`) for decoupled processing, and an alert topic for real-time administrator emails.

### 2. Configuration & Deployment Layer (Ansible)
Ansible manages the complete lifecycle of the servers, utilizing dynamic inventory generation:
* **Dynamic Inventory & Secrets Management:** Terraform generates the `inventory.ini` file dynamically, injecting the live IPs of the EC2 instances alongside AWS resource endpoints (RDS, S3, SQS, SNS) and database passwords. **This file is strictly excluded from Git** via `.gitignore` to maintain absolute security.
* **Role-Based Execution:** The Playbook utilizes strict conditional tasks (`when: server_type == "..."`) to ensure the Backend API container only runs on the Backend server, while the SQS Listener container only runs on the designated Worker server.
* **Reverse Proxy:** Ansible configures Nginx to act as a secure Reverse Proxy, routing HTTP traffic on port 80 directly to the Docker containers running on port 5000.

---

## 🔐 Security & Secrets Management
This project strictly adheres to DevOps security best practices:
* **No Hardcoded Secrets:** Private keys (`.pem`), database passwords, and runtime environments (`.env`) are **never** committed to version control.
* **Local Secrets File:** Sensitive deployment variables, such as the RDS master password, are managed via a local `secrets.auto.tfvars` file. This file is strictly excluded from Git via `.gitignore` to maintain absolute security.
* **Template Generation:** Ansible utilizes an `env.j2` template file to dynamically build the production `.env` file directly on the target servers during deployment.
* **Example Files Provided:** An `env.example` file is included in the repository to demonstrate the required environment variables without exposing sensitive data.
* **SSH Bastion Host (ProxyJump):** Ansible accesses the private subnets (Backend & Worker) securely by tunneling SSH connections through the public Frontend server.

### Security Enhancements & Network Isolation
To enforce a strict and secure 3-tier architecture, the internal network routing has been refactored:
* **Private Tier Isolation:** Backend and Worker EC2 instances are now explicitly deployed within Private Subnets and do not receive public IP addresses (`associate_public_ip_address = false`).
* **Secure Outbound Traffic:** An Internet Gateway (IGW) routing strategy is utilized to simplify connectivity and reduce costs. The private route tables direct outbound internet traffic via the Internet Gateway, while security groups strictly block unauthorized inbound traffic, ensuring instances remain isolated from direct external access.

## 🛠️ Troubleshooting & Lessons Learned
During the development of this project, I encountered and resolved several technical challenges that provided deep insights into IaC and cloud infrastructure:

1. **Database Hostname Resolution:**
   - **Problem:** The application failed to connect to the RDS database with the error `could not translate host name`. It turned out that the Terraform `db_instance_endpoint` output included the port number (e.g., `:5432`), which caused connectivity issues when injected into the application's environment variable.
   - **Solution:** I updated the Terraform output logic to use `db_instance_address` (which provides only the hostname) instead of `endpoint`, ensuring seamless connectivity.

2. **SQS Resource Conflict:**
   - **Problem:** Attempting to provision an SQS queue via Terraform failed because a queue with the same name already existed in the AWS account from a manual test, leading to a `QueueAlreadyExists` error.
   - **Solution:** I followed IaC best practices by versioning the resource name (`mission-queue-v2`) and ensuring that all future resource lifecycle management is strictly controlled through Terraform's state file.

3. **Dynamic Inventory vs. Hardcoding:**
   - **Problem:** Managing environment variables that are determined only at runtime (like RDS and S3 endpoints) initially seemed to require manual updates.
   - **Solution:** I implemented a dynamic pipeline where Terraform generates the `inventory.ini` file upon every `apply`, ensuring that Ansible always receives the most up-to-date infrastructure metadata without any manual intervention.
